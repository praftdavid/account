## 0. 시작 전 — 반드시 먼저 읽을 것

세 파일을 먼저 정독하라. 특히 설계 문서의 **§4 설계 원칙**과 **§8 마감·투자평가 규칙**은 구현 내내 지켜야 하는 불변 규칙이다. 임의로 스키마나 회계 처리 방식을 바꾸지 말고, 바꿔야 할 근거가 보이면 먼저 사용자에게 확인하라.

---

## 1. 목표와 비목표

- **목표**: 분개(수기 + 추후 자동)를 입력하면 시산표·재무제표·이익잉여금처분계산서·자본변동표까지 산출하는, 프래프트 전용 관리회계 앱.
- **비목표 (절대 만들지 말 것)**: 홈택스 연동, 전자세금계산서 발행, 부가세·원천세·급여·4대보험 **신고 기능**. 세무 신고는 세무사가 담당한다. 이 선을 넘지 말 것.

## 2. 기술 스택

- **DB/백엔드**: Supabase (PostgreSQL + Auth + 자동 REST/Realtime API)
- **프론트엔드**: 사용자의 **기존 웹앱을 재사용·진화**시킨다. 새로 짜지 말고, 먼저 현재 코드와 스택을 파악한 뒤 데이터 계층만 Supabase로 교체·연결하라.
- **모바일(추후)**: Capacitor로 웹앱을 iOS 앱으로 래핑. 지금 단계에서는 구현하지 않되, 웹 표준을 벗어나는 브라우저 전용 API 사용은 피해 나중에 래핑이 쉽도록 하라.

## 3. 초기 셋업 순서

1. **Supabase 프로젝트 준비** — 프로젝트 생성과 API 키(anon/service) 발급은 **사용자가 대시보드에서 직접** 한다. 너(Claude Code)는 자격증명을 생성·입력하지 않는다.
2. **자격증명 주입** — Supabase URL과 anon key는 사용자가 `.env`(또는 환경변수)에 넣는다. 키를 코드에 하드코딩하지 말 것.
3. **마이그레이션 적용** — `praft_schema.sql` → `praft_seed.sql` **순서대로** 실행. (Supabase SQL Editor 또는 supabase CLI `db push`.)
4. **RLS(행 수준 보안) 설정** — 단일 사용자/가족 법인용이라도 인증된 사용자만 접근하도록 RLS 정책을 기본 활성화하라.
5. **연결 확인** — 계정과목 40건, 회계기간 2건이 조회되는지 스모크 테스트.

## 4. v1 빌드 순서 (뼈대부터 — 빅뱅 금지)

닫힌 루프를 하나씩 완성하며 올라간다.

1. **계정과목 마스터 UI** — 조회 + 추가/수정. 추가 폼에 반드시 포함: 계정명·코드·유형·정상잔액·부모계정·`std_report_code`. (사용자가 계정을 쉽게 늘릴 수 있어야 한다.)
2. **수기 분개 입력** — 전표(header) + 분개상세(lines). 차변합=대변합을 화면에서 실시간 검증. 저장 시 `draft`, 확정 시 `posted`.
3. **계정별원장** — 계정 선택 → 일자순 + 누적잔액.
4. **잔액시산표 / 합계잔액시산표** — `v_trial_balance` 뷰 활용.
5. **손익계산서 · 재무상태표 · 손익내역표** — 시산표를 `account_type`·`statement_section`로 집계. 손익내역표는 `parent_account_id` 계층 세부.
6. **이익잉여금처분계산서 · 자본변동표** — 자본계정 기초잔액 + 기중 증감 roll-forward. 기초잔액은 최초 1회 **개시 분개(`source_type=opening`)**로 주입(기존 앱 데이터 이관).

## 5. 구현 시 반드시 지킬 규칙

- **단일 진실원천**: 모든 재무제표는 `journal_lines`(posted) 위의 조회/뷰로 도출한다. 집계값을 별도 테이블에 중복 저장하지 말 것.
- **draft/posted**: 자동·수기 분개 모두 `draft`로 시작, 사용자 승인 시 `posted` 전기. 스키마의 균형 검증 트리거는 **posted에서만** Σ차=Σ대를 강제한다(트랜잭션 커밋 시점, deferred).
- **부문 이중 뷰**: 관리 손익은 `journal_lines.segment`로 group by. 법정/표준재무제표는 `segment`를 무시하고 전사 합산 + `std_report_code` 매핑. **한 번 기록, 두 뷰** — 이중 기장 금지.
- **투자 평가(OCI 재분류)**: 기말 평가익은 `매도가능증권평가익`(자본)에 계상(손익 미경유). 매각 시 해당 종목의 누적 OCI를 환입하고 실현손익을 `금융매출`(영업)로 대체. 종목별 원가·OCI는 `securities_lots`(FIFO)로 추적.
- **마감/개시 분개**: 마감 시 손익→이익잉여금 대체를 `source_type=closing` 전표로 기록하고 `fiscal_periods.status`를 closed로. 전기말 자산·부채·자본 잔액이 곧 당기초 잔액(별도 기초잔액 테이블 없음).
- **보안**: 자격증명은 사용자가 주입. 키·비밀번호를 코드/커밋에 넣지 말 것.

## 6. 이후 단계 (v1 이후, 지금 착수 X)

- **자동 분개 파이프라인**(설계 §6) — 은행·증권 업로드 → 6단계. 코어 안정화 후 별도 계층으로.
- **v1.5** — 현금흐름표, 예상 법인세 산출표(세무조정). `tax_rules` 규칙 테이블로 외부화.
- **표준코드 매핑** — 1기 표준재무제표 확보 후 `std_report_code` 채우기.
- **급여 부기** — 급여대장 → 자동 분개(또 하나의 입력 경로). *신고는 여전히 세무사.*

## 7. 첫 마일스톤 (권장)

**M1 = 닫힌 루프 하나**: Supabase 연결 → 계정과목 CRUD → 수기 분개 입력(draft/posted) → 시산표 표시. 여기까지 되면 회계 엔진의 심장이 뛰는 것. 이후 재무제표를 하나씩 얹는다.
